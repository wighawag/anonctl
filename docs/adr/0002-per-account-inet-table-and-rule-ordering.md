# The per-account fail-closed `inet` nftables ruleset: table/chain naming, priorities, and rule ordering

Status: accepted (amended: the base chains now only ever JUMP on a POSITIVE `meta skuid` match, and fail-closed lives in a per-UID closure chain ending in an unconditional terminal DROP -- see "Positive-match base chains" below)

## Context

The kernel half of anonctl's forcing is one `nftables` ruleset per anon account. It was hand-validated end-to-end (`work/notes/findings/manual-per-uid-tor-recipe.md`) as a single `inet table anonctl` with a `nat_out` (dstnat) and a `filter_out` (drop-policy) chain. The Go generator (`internal/nftables`) encodes that proven recipe verbatim, but the manual recipe was for ONE account on one host; anonctl runs many accounts and applies the rules itself. That surfaced a few decisions the recipe did not have to make. This is the highest-stakes code path (a wrong rule silently leaks a real IP or locks a user out), so the decisions are recorded here.

## Decisions

- **Per-account table name `anonctl_<account>`, not the recipe's shared `anonctl`.** Multiple anon accounts coexist; a single shared table would make each account's Apply clobber the others. Naming the table per-account lets Apply/Delete scope to exactly one account and leave every other table (the whole rest of the host firewall) untouched, which is also what makes the shared-write isolation acceptance test possible. nft identifiers cannot contain `-`, so a named account's `-` becomes `_` (`anon-work` -> `anonctl_anon_work`); this only names the table, never the Unix account.

- **Chain priorities are kept exactly as validated: `nat_out` at `dstnat` (-100) and `filter_out` at `filter` (0).** The recipe proved (with a scratch counter) that a REDIRECTed packet re-enters the filter hook with its destination already rewritten to the shim port, so `nat` must run before `filter` and the filter accepts match the SHIM ports, not the original destination. Reordering or re-prioritising either chain breaks that invariant.

- **Within the anon UID's closure chain, rule ORDER is load-bearing and fixed:** the endpoint DROP for the anon UID (closure b) is emitted BEFORE the shim-port ACCEPT (closure a), so an anon-UID dial of the endpoint can never be shadowed into an accept; the shim-port ACCEPT is emitted before the broad `127.0.0.0/8` DROP, so the account's own shim ports are not swallowed by the loopback drop; and every exemption ACCEPT precedes the TERMINAL DROP that now ends the chain. All of these orderings are asserted in the unit tests by index, not just by presence, because a first-match firewall is only as correct as its ordering. (These rules lived directly in the `filter_out` base chain until the amendment below moved them into `anon_filter`; their relative order is unchanged.)

- **The load is idempotent via a create-if-absent + `delete table` preamble, applied with `nft -f -` (stdin).** The generated text begins `table inet <t> {}` then `delete table inet <t>` then the real definition, so a re-Apply is an atomic REPLACE of that one table (never an append of stale rules) and never touches another table. Delete issues only `delete table inet <t>`, never `flush ruleset`.

- **The endpoint host must be an IP literal (v4 or v6), and closure (b) uses the matching `ip`/`ip6` family.** A hostname in a firewall rule is ambiguous and a DNS-lookup-at-rule-time is itself a leak vector; and picking the family from the endpoint's actual address keeps closure (b) from being silently v4-only for a v6 endpoint. Generation rejects a non-literal host loudly rather than emit a rule that half-forces.

## Positive-match base chains and the terminal drop (amendment)

**The RULES above are unchanged; WHERE they live, and HOW a packet reaches them, changed, because the original entry condition was a box-wide bug.** `filter_out` was a base chain on the output hook with `policy drop`, and its only pass-through for uninvolved UIDs was a NEGATIVE match: `meta skuid != <anon> meta skuid != <shim> accept`.

- **Not every locally generated packet carries a socket UID.** `meta skuid` reads `sk->sk_socket->file`, which is unavailable for a large share of ordinary TCP output. Measured on loopback (kernel 6.18) with a policy-accept classification chain: of the packets a single 600KB transfer emitted, the bulk data super-packets, the pure ACKs and the FIN carried NO attributable socket owner, while SYN and SYN-ACK always did. Data retransmissions on an ESTABLISHED socket are in the same unattributable class.

- **A SYN is attributable, INCLUDING a retransmitted one, and this is the single premise the fix rests on, so it was measured rather than assumed.** It is not obvious: a SYN whose transmission was dropped is retransmitted from TIMER context, which is exactly where attribution is normally lost, and a dropped SYN is never confirmed in conntrack, so its retransmission arrives as a FRESH connection and re-traverses `nat_out`. Were it unattributable it would take no jump, keep its real off-box destination, and escape both tables with the host's real address (and the OLD negative-match shape would have caught it by accident, making this a regression rather than a fix). Measured over a 20-second dial to an unroutable destination, counted before either table: 9 v4 SYNs and 9 v6 SYNs, each one original plus 8 retransmissions, ALL attributable. With the forcing and baseline tables loaded together, ZERO packets escaped with an off-box destination; with no tables loaded, all 9 of each escaped, which is the control that makes the zero meaningful.
- **Such a packet matches neither `skuid == u` nor `skuid != u`.** It therefore took no `accept`, fell through, and was killed by the `policy drop`. Because a `drop` verdict is TERMINAL across ALL base chains at a hook (ADR-0005), one account's forcing table was enough to do this, and a host with N forced accounts had N such chains.
- **The blast radius was the whole box, not the account.** Every uid's larger TCP transfers stalled: the kernel counted `TcpExtTCPRetransFail`, the RTO backed off past 50 seconds, and the transfer hung with no error on either side. Small transfers never retransmit, so they looked fine, which is why this was misdiagnosed for a while as an application bug. Measured against the old ruleset in a namespace: ten 600KB loopback transfers as an UNINVOLVED uid, 0/10 completed, `TcpExtTCPRetransFail` +78, and 169 of 351 packets adjudicated away. The same ruleset passed 10KB transfers while still silently dropping 11 of 121 packets.

**The decision: a base chain must never adjudicate a packet it cannot attribute.** Both base chains are now `policy accept` and contain NOTHING but positive-skuid jumps into per-UID regular chains:

```
chain nat_out     { type nat    hook output priority dstnat; policy accept; meta skuid <anon> jump anon_nat }
chain filter_out  { type filter hook output priority filter; policy accept; meta skuid <shim> jump shim_filter
                                                                            meta skuid <anon> jump anon_filter }
```

An unattributable packet takes no jump, reaches the end of the base chain, and is accepted by policy. Every DROP now lives inside a chain that is only ever entered after a positive UID match, so anonctl can only drop traffic it has positively attributed to an account it governs. The per-rule `meta skuid <uid>` qualifiers inside the closure chains are kept even though the jump already established the UID: they cost nothing, keep each rule self-describing, and keep the exemption `accept` spelled IDENTICALLY to the nat `return` and the baseline `return` (all three come from the shared `exemptMatch`, and `work/notes/findings/split-tunnel-broken-by-exemption-blind-baseline.md` records what happens when those three diverge).

- **`anon_filter` MUST end in an unconditional, unqualified, LAST `drop`, and that rule carries real weight.** The anon UID's real egress used to be dropped by the base chain's POLICY, not by any rule. Flipping the policy to `accept` without this terminal rule would not degrade the jail, it would REMOVE it. The traffic that proves it is the anon UID's ICMP and its non-53 UDP: neither is redirected by `nat_out`, so both arrive at the filter hook with their real off-box destination and are matched by nothing above the terminal drop. Those are exactly the `verify` assertions `icmp-drop` and `non-tcp-udp-drop`. Measured with the forcing table loaded ALONE in a namespace: with the terminal drop present both are dropped; with only that one line removed, both escape. On a real host the standing baseline table would drop them too, so the regression would present as "everything still passes" while the forcing table had silently stopped forcing. Pinned by `TestAnonClosureChainEndsInAnUnconditionalTerminalDrop` (text) and `TestAnonUIDIsStillDroppedByAnExplicitRule` (behaviour, with the baseline deliberately not loaded so it cannot mask the fault).
- **The terminal drop is the ONE rule that must NOT carry a `meta skuid` qualifier.** Qualifying it would re-introduce the original bug inside the closure chain. It is safe unqualified precisely because the chain is unreachable except through a positive UID match.
- **`shim_filter` needs no terminal rule.** Falling off its end returns to `filter_out` and is accepted by policy, which is the same verdict its own catch-all `accept` gives.
- **`nat_out` got the same treatment, and its old hole was worse than a drop.** `meta skuid != <anon> return` let an unattributable packet fall through to `meta l4proto tcp redirect to :<relay>`, i.e. an UNINVOLVED uid's traffic redirected INTO the anon shim. Measured: a nat base chain is evaluated ONLY for the first packet of a conntrack flow (10 evaluations across a 323-packet flow, one per connection, 0 reaching the catch-all redirect), and a new flow's SYN is always attributable, so the hole was masked in practice. "Masked by conntrack" is not a closure, so the positive form removes it outright.
- **Why not `ct state established,related accept` at the top of the chain.** It would work, and it was rejected: it makes correctness depend on flow state rather than on structure, and it does not fix `nat_out`. The structural fix cannot have this class of bug by construction, and it adds no conntrack cost. (Note the premise that the design "avoids conntrack" is false as it stands: registering `nat_out` enables conntrack for the whole namespace. Measured: 0 conntrack entries with no forcing table loaded, 10 entries after ten uninvolved-uid loopback connections with it loaded. Loopback traffic IS tracked wherever anonctl is installed. That is a separate observation, and it does not change this decision.)
- **The fail-closed property is unweakened, and rests on the FIRST packet.** A new connection's SYN always carries a socket UID, and so does every retransmission of it (measured above), so it is always adjudicated by these rules. An unattributable follow-on packet necessarily belongs to a flow whose SYN was already judged and, for the anon UID, already REDIRECTED to a loopback shim port by `nat_out` -- a rewrite conntrack then applies to every later packet of the flow regardless of attributability. So the weight is carried by the filter match for the first packet of a flow, and by the DESTINATION REWRITE for everything after it.

## Consequences

The ports the rules redirect to (the shim's per-account relay + DNS ports) and the UIDs are `Params` inputs, resolved by the caller (the persistence/wiring task) from the account/shim names and the shim binary's defaults (19050/19053), exactly as the recipe embeds them. IPv6 remains drop-only (there is no v6 redirect target), matching the recipe's documented, deliberate property: the anon account has no IPv6 connectivity, but it never leaks over v6.
