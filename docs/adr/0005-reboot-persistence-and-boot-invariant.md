# Reboot persistence: templated per-account shim unit, an anonctl-owned early loader, a standing default-deny, and the boot invariant

Status: accepted (amended twice: the boot invariant now holds by a standing default-deny + anonctl's own loader, not an nftables.service drop-in; `rm` teardown now STOPS the shim unit BEFORE it userdels the shim account; and the units now live in `/usr/local/lib/systemd/system`, are enabled by anonctl's OWN `.wants` symlinks rather than `systemctl enable`, and name RESOLVED absolute binary paths -- see "Portable unit install and enablement" below)

## Context

An anon account's forcing must SURVIVE a reboot and re-apply FAIL-CLOSED, with no window where the anon UID has un-anonymized egress at boot (the BOOT INVARIANT: "at no point during boot does the anon UID have direct egress"). anonctl applies everything itself as root (the ufw stance) and does NOT own the endpoint's lifecycle. This task (`persistence-and-boot-invariant`) chose the persistence mechanism and the unit shape; several decisions are load-bearing and would surprise a future reader, so they are recorded here.

**CORRECTION (from the e2e finding, BUG 1).** The original decision below claimed the boot invariant "holds by construction because nftables.service loads early." That was FALSE on a default Debian host: anonctl persisted its ruleset via a drop-in on the host's `nftables.service`, but Debian ships that service DISABLED and anonctl never enabled it, so after a real reboot the forcing rules were ABSENT and the anon UID egressed with the host's real public IP in the clear (`{"IsTor":false,"IP":"51.7.210.66"}`). Chasing the invariant by "loading the allow-through-shim rules early enough" was the WRONG invariant: it meant "un-forced" could mean "free" during any window the rules were not (yet) loaded. The mechanism was inverted and the loader replaced; see the amended decisions.

## Decisions

- **The per-account shim is a systemd `@`-template unit (`anonctl-shim@<account>.service`), NOT one multiplexer process for all accounts.** The per-account process boundary IS the security boundary: each account's shim runs under its OWN dedicated shim UID (closure b: only the shim UID may reach the endpoint), so a single multiplexer would collapse that boundary. systemd's `@`-template gives every account its own supervised instance from ONE unit file; `add` runs `enable --now`, `rm` runs `disable --now`, `update` runs `restart` (to pick up a rewritten endpoint). One template file, N independent instances, N distinct shim UIDs.

- **The template unit is account-AGNOSTIC; per-account parameters come from a per-instance `EnvironmentFile` (`/etc/anonctl/shim/<account>.env`).** `%i` is the account (the instance), and the shim UID, loopback ports, endpoint address, and derived isolation username are read from the env file, so ONE template serves every account. The unit starts as root only long enough to `setpriv --reuid ${ANONCTL_SHIM_UID}` down to the account's dedicated shim UID (exactly as the validated recipe runs the shim); the shim itself never runs as root. `User=` was rejected because it cannot read a per-instance env var, and baking the UID into the unit would break the single-template property.

- **Unit ordering is `After=network.target` only; the shim deliberately does NOT `Wants=`/`After=` the endpoint's own service.** anonctl does not own the endpoint lifecycle (it does not manage `tor.service`), and the nft rules FAIL CLOSED (drop) if the endpoint is not yet up, so there is no leak window to order against: the worst case is dropped-until-shim-and-endpoint-are-up, never leaking. `add` prints a reminder to enable the endpoint (e.g. `tor.service`) at boot, since that is the operator's job.

- **The boot invariant is inverted: the anon UID's RESTING STATE is a standing per-UID DEFAULT-DENY, and forcing only ever OPENS the shim path.** Each account has a tiny, standalone `inet` table (`anonctl_baseline_<account>`, `internal/nftables.GenerateBaseline`), SEPARATE from the per-account forcing table, whose sole job is: for the anon UID, RETURN loopback destinations and DROP everything else (all real, non-loopback egress, v4 AND v6). It is applied at `add`-time BEFORE the forcing rules and the shim, and persisted as its own always-loaded `<account>.baseline.nft`. The precise invariant it guarantees: **an anon UID with no anonctl forcing loaded is DROPPED, not free; forcing only ever OPENS the shim path.** If the forcing rules fail to load, the shim is down, or the endpoint is down, the account is STILL dropped, by construction. This is strictly safer than "load the allow-rules early enough."

- **Why this layers WITHOUT dropping forced traffic (the load-bearing nftables semantics).** A `drop` verdict is TERMINAL across all base chains at a hook; an `accept` is NOT (a later chain can still drop). So the baseline cannot simply drop the anon UID (that would kill forced traffic too). Instead, forcing's nat/output chain runs at `priority dstnat` (-100), BEFORE every filter chain, and REDIRECTS the anon UID's egress to a LOOPBACK shim port (rewriting the destination). The baseline (a filter/output chain, policy ACCEPT so it never touches another UID) RETURNs loopback (handing forced/shim traffic on to the forcing table's own closures) and DROPs everything non-loopback. Forcing present => the anon UID's traffic is redirected to loopback, the baseline returns it, the forcing table governs it (shim path works). Forcing absent => no redirect, the real egress stays non-loopback, the baseline DROPS it.

- **The baseline MUST RETURN the LAN exemptions, not just loopback (the split-tunnel corollary of the same nftables semantics).** A LAN exemption (story 25, ADR-0006) is the ONE class of anon-UID egress that is deliberately NOT redirected into the shim: the forcing nat chain `return`s the exempted destination so it egresses the real NIC directly, and the forcing filter chain `accept`s it. But that `accept` is non-terminal, and the baseline (same `output` / `priority filter` hook) `drop`s everything non-loopback. Because a `drop` is terminal across chains at a hook, the baseline's broad `ip daddr != 127.0.0.0/8 drop` KILLS the un-redirected exempted flow BEFORE the forcing `accept` can matter. So the baseline must ALSO `return` each exempted destination (`internal/nftables.GenerateBaseline` takes the exemption set and emits `meta skuid <anon> <exemptMatch> return` before its broad drop, reusing the SAME `exemptMatch` clause the forcing return+accept use, so the three can never diverge). This is consistent with the exemption's contract: an exempted private destination is reachable DIRECTLY regardless of the anonymizer's state (forcing present or absent), because it is explicitly carved out of the forced path, not anonymized traffic. The threading runs end-to-end: `forcing.Install` and `forcing.Reconfigure` pass the parsed exemptions to `ApplyBaseline` (so an `update --allow` updates the LIVE baseline, not only the persisted file), and `systemd.WriteAccount` re-parses the account's persisted raw exemptions into the persisted `<account>.baseline.nft` so the boot loader restores the return too. The symptom this closes (from a real Tailscale host): the exemption was generated correctly in BOTH forcing chains, yet the anon UID REACHED non-exempt LAN hosts (redirected into the shim) and TIMED OUT on the single EXEMPTED host (dropped by the exemption-blind baseline); `verify`'s `split-tunnel-tight` correctly reported the hole broken. It passed in isolation only because the nftables integration test loaded the forcing table WITHOUT the baseline; the fix adds a baseline-loaded exemption-return assertion so the two tables are proven together.

- **The nftables ruleset is loaded at boot by anonctl's OWN early loader unit (`anonctl-nftables.service`), NOT a drop-in on the host's `nftables.service`.** The unit `nft -f`s anonctl's per-account rule files (both the baseline and the forcing tables) from `/etc/anonctl/nftables/*.nft`; it is `WantedBy=sysinit.target`, `DefaultDependencies=no`, `Before=network-pre.target`, so it loads BEFORE the network is up and does NOT depend on the host's `nftables.service` (which Debian ships DISABLED and a later `systemctl disable nftables` could silently re-disable). anonctl OWNS this unit, so `add` enabling it mutates no host-owned service; `rm` on the LAST account disables it. The loader iterates the glob, so an empty/absent rules dir is a clean no-op and boot never fails when no account is forced. This REPLACES the earlier drop-in, whose reliance on a host-owned, silently re-disableable service caused the reboot leak. `add` still applies the LIVE rules itself via `nft`, so the unit only needs to fire at the NEXT boot (it is enabled without `--now`).

- **The boot invariant is proven by a reboot-EQUIVALENT early-boot simulation, not a real reboot.** The integration tests load the persisted rules the loader would `nft -f` at boot (the baseline AND the forcing table) with the shim NOT running, reproducing the boot window, then assert AS the anon UID that a direct outbound connection is DROPPED. They also prove BOTH directions of the inversion: forcing-ABSENT (only the baseline loaded, or the forcing table flushed) => DROPPED (the new guarantee, and the exact post-reboot state the finding observed leaking), and forcing-PRESENT => the redirect-into-shim path is intact (the baseline does not drop the redirected loopback traffic). They isolate to throwaway account/tables + a planted sentinel and assert the host's rules are untouched. The DEFINITIVE proof remains a real-host reboot: a human re-run of the e2e validation's step 5, PLUS a "flush the forcing table, confirm still dropped" check, is the final gate.

## Portable unit install and enablement (amendment, 2026-09-20)

**The mechanism that WIRES UP the boot invariant moves; the invariant itself is unchanged.** The decisions above still hold (standing baseline default-deny, anonctl's own early loader, the `@`-template per-account shim). What changed is WHERE those units live, HOW they are enabled, and WHAT paths they name, because all three were silently Debian-specific and the middle one made anonctl uninstallable on NixOS. Evidence: `work/notes/findings/systemd-enablement-target-and-nixos-fhs-gaps.md`.

- **The units install into `/usr/local/lib/systemd/system`, not `/etc/systemd/system`.** On NixOS `/etc/systemd/system` is a symlink into the READ-ONLY Nix store, so anonctl could not write its units at all and `add`/`rm`/`verify` were all unusable. systemd's own load-path table calls the chosen dir "System units installed by the administrator", which is precisely what anonctl is, and it is in the default search path on Debian AND NixOS, so ONE default serves both and nothing does a distro check. `/run/systemd/system` was REJECTED despite being writable on NixOS: it is cleared at boot, and forcing that evaporates on reboot is strictly worse than no forcing, because the account still exists and still looks anonymized. That is the same class of failure as BUG 1 above, arrived at from the opposite direction.

- **A migration sweep is MANDATORY, because the old dir OUTRANKS the new one.** `/etc/systemd/system` sits ABOVE `/usr/local/lib/systemd/system` in the unit load path, so a unit file left behind after an upgrade SHADOWS the newly installed one and the host keeps running the OLD definition while the operator believes they have upgraded. `Store.MigrateLegacyUnits` removes anonctl's own unit files and enablement symlinks (including every per-account shim INSTANCE) from the legacy dir, and fails LOUD if it cannot, rather than leaving two definitions of the same unit.

- **anonctl creates its own enablement symlinks instead of calling `systemctl enable`.** This is the decision that actually unblocks NixOS, and it is not obvious: `systemctl enable` writes its symlink into the CONFIG dir for the scope (`/etc/systemd/system`) REGARDLESS of where the unit file lives, so relocating the unit does not relocate its enablement, and the enable still fails on a read-only `/etc`. systemd reads `<target>.wants/` from EVERY directory in the unit load path, so anonctl writes `<unitdir>/multi-user.target.wants/anonctl-shim@<account>.service` and `<unitdir>/sysinit.target.wants/anonctl-nftables.service` itself. `add` therefore does enable-then-`start` as two steps rather than `enable --now`, and `rm` does `stop`-then-unlink.

  ONE mechanism is used on BOTH distros rather than "systemctl where it works, symlinks where it does not". A fail-closed forcing tool must not have a boot-persistence path that is only ever exercised on one distro; this way every Debian test run exercises the NixOS path too. The accepted COST is that `systemctl is-enabled` reports `disabled` for these units even though they are genuinely wired to start at boot, because `is-enabled` inspects only the config dir. That is a real observability regression for anyone reading a host by hand, and it is why `Store.IsUnitEnabled` exists and why `verify` must never ask `is-enabled` (it would be a false negative; `systemctl show <target> --property=Wants` is the honest probe).

- **Ordering inside `add` is load-bearing, and two of its steps are ordered against a FAIL-OPEN failure rather than a fail-closed one.** First, the binaries are resolved BEFORE `provision.Add` creates the account (`systemd.PreflightUnitBinaries`, and again at the top of `forcing.Install` before any mutation). Resolving them LATE would abort with the account already created and the live rules applied but NO unit installed, so the next boot would load neither the baseline nor the forcing: the account exists and egresses with the host's real IP. That is fail-OPEN, and strictly worse than the pre-0.4 behaviour it would replace (where a missing shim still left an enabled loader, so the baseline loaded and the account was merely DROPPED). Second, the units are ENABLED before the legacy dir is swept: both orders converge if the sequence completes, but only enable-then-migrate is safe if it is INTERRUPTED, since migrate-then-enable can leave the loader enabled in neither location. Nothing is re-read by systemd until the single `daemon-reload` at the end, so enabling first cannot expose a double definition.

- **The migration ADOPTS enablement, it does not merely delete it.** The legacy sweep necessarily matches every `anonctl-shim@*.service` link, but the `add` that triggers it re-creates only the ONE account being added. A delete-only sweep would therefore silently de-enable every OTHER account on a multi-account host: their shims keep running, so nothing looks wrong until the next reboot, when they never start. So each enablement symlink is re-created in the new unit dir BEFORE its legacy copy is removed (which also means an interrupted migration never leaves an account enabled nowhere).

- **Every binary named in a generated unit is RESOLVED at install time, and an unresolvable one ABORTS `add`.** The units hard-coded `/usr/bin/setpriv` and `/usr/sbin/nft`; neither exists on NixOS, where `/usr/bin` holds only `env` and `/bin` only `sh`. The shim failure is fail-CLOSED (the baseline still drops, the account merely breaks). The LOADER failure is fail-OPEN and silent, and it is the important one: the loader is what installs the standing baseline default-deny at boot, so if it cannot run `nft`, the inversion this ADR rests on never happens and the anon UID egresses freely with the host's real IP, with the account and its marker looking intact. A unit must therefore never be written naming a binary that was not resolved: the failure has to surface at install time, not at the next boot. The paths stay ABSOLUTE (a unit has no useful inherited `$PATH`); what changed is that they are resolved rather than assumed.

- **The shim's path is resolved from the ACTUAL install location** (sibling of the running `anonctl`, then `$PATH`, then the conventional `/usr/local/bin/anonctl-shim` if it really exists), closing a second FHS assumption: the unit used to hard-code `/usr/local/bin/anonctl-shim` regardless of `$PREFIX`, which `install.sh` compensated for by symlinking that path. That workaround is gone, and a custom `PREFIX` now simply works. `verify`'s own anon-UID probe uses the SAME resolution, because a probe pinned to `/usr/local/bin` would leave the trust anchor unusable on precisely the hosts this change targets.

- **The resolved path is baked VERBATIM: never resolve the symlink.** This is a second, delayed-action form of the same fail-open bug, and it is easy to reintroduce while "tidying up" the code. On NixOS every tool has two absolute paths:

  ```
  /run/current-system/sw/bin/nft                            <- STABLE: repointed on every rebuild
  /nix/store/<hash>-nftables-1.1.6/bin/nft                  <- what EvalSymlinks/realpath/readlink -f gives
  ```

  `exec.LookPath` returns the `$PATH` entry verbatim, which is the stable one, and `filepath.Abs` preserves it (it only `Clean`s an already-absolute path). `filepath.EvalSymlinks` would return the store path, which is correct on the day it is written and WRONG the moment the package is updated or the system rebuilt: the old store path is garbage-collected, `ExecStart` points at a file that no longer exists, the loader fails `203/EXEC`, and the account is silently unjailed with no baseline default-deny. That failure would surface weeks after the install with nothing in the config having changed, which makes it far harder to diagnose than the original bug. On Debian `LookPath` yields `/usr/sbin/nft` and the identical code works, so this is one code path, not a distro branch. Pinned by `TestResolverBinaryNeverBakesAResolvedSymlinkTarget`.

  The same trap catches the SHIM by a different route: `os.Executable()` resolves symlinks (it reads `/proc/self/exe`), so the "sibling of the running anonctl" rule yields a store path whenever anonctl is itself invoked through a stable symlink, which is the normal shape of a Nix-packaged install. `Resolver.preferStableAlias` therefore swaps in a `$PATH` entry when one names the SAME file (compared by inode; the resolved target is never returned), and keeps the sibling when `$PATH` holds a genuinely different binary, preserving version coherence between `anonctl` and `anonctl-shim`.

  `/bin/sh` in the loader's `ExecStart` is the one path still written literally. It exists on both targets (it is the last surviving entry in NixOS's `/bin`), and resolving it would be circular, since the resolution itself needs a shell-free absolute path. Noted so the "every binary is resolved" claim above is read precisely.

## Teardown ordering (amended from the e2e finding, BUG 1)

**CORRECTION (from `work/notes/findings/e2e-binary-revalidation.md`, PART E / BUG 1).** `add` and `rm` mutate two things per account: the login + dedicated shim UNIX ACCOUNTS (`internal/provision`, via `useradd`/`userdel`) and the FORCING artifacts (the nft tables, the persisted files, and the per-account shim UNIT `anonctl-shim@<account>.service`, via `internal/forcing` + `internal/systemd`). These are removed by two different calls, so their ORDER is load-bearing on teardown and is fixed here.

- **`rm` disables --now the shim unit BEFORE it userdels the shim account.** The dedicated shim service account (`<account>-shim`) is the UID the `anonctl-shim@<account>.service` unit runs as. `userdel` REFUSES ("user is currently used by process", exit 8) while any process runs as that UID. The original `runRm` called `provision.Rm` (userdel) BEFORE `forcing.Remove` (which `systemctl disable --now`s the shim), so on the LAST account a single `anonctl rm --purge-account` aborted at the userdel with the shim still running, and the entire last-account cleanup (nft tables, marker, `/etc/anonctl`, the shared template + loader units) never ran, leaving exactly the residue this ADR's cleanup was meant to prevent. The correct, now-enforced order is: **disable --now the shim unit -> remove the nft tables + config + marker -> userdel the login + shim accounts -> (last account) remove the shared units + empty dirs.** `forcing.Remove` already disabled the shim first internally; the fix was to sequence `forcing.Remove` BEFORE `provision.Rm` in `runRm` (they are the two seams, so the order lives at the caller). The ordering is asserted at the `runRm` seam by a unit test (the disable-shim call is recorded before the shim userdel) and proven no-residue by an `integration`-tagged teardown against a throwaway account whose shim UID is genuinely held by a running unit, with the host's other nft rules asserted untouched.

- **Teardown is proceed-and-report, not abort-on-first-error.** `runRm` runs every teardown step (remove forcing, userdel, remove marker) even if an earlier one failed, surfacing the first error with a non-zero exit. A half-torn-down account that silently stopped on the first error is worse than a fully-attempted, reported partial: the correct ordering makes the common path complete cleanly, and proceed-and-report makes an unexpected mid-teardown failure leave the least residue it can while still failing loudly.

## Consequences

Persistence introduced a per-account at-rest config (`internal/accountconfig`, `/etc/anonctl/accounts/<account>.json`, root-only 0600) as the source of truth the boot re-apply and `update` read; it is deliberately SEPARATE from the world-readable, credential-free marker (it may carry the endpoint address the marker must never hold). The `update`/`reconfigure` verb re-applies the nft rules (an atomic table replace: the default-DROP is never absent) BEFORE restarting the shim, so a reconfigure has no un-anonymized window. `add` gained an `--endpoint` flag (default: the local Tor SocksPort); `update`/`reconfigure` require it.
