# The two shared units are exportable, and a host may own them; the per-account symlinks are never exportable

## Status

Accepted (0.9.0).

## Context

anonctl installs exactly two account-AGNOSTIC unit files: the shim `@`-template (`anonctl-shim@.service`) and the early-boot nftables loader (`anonctl-nftables.service`). Both are written into `/usr/local/lib/systemd/system` by `add`, for the reasons ADR-0005 records: `/etc/systemd/system` is a read-only store symlink on NixOS, and `/run/systemd/system` is cleared at boot, so forcing installed there would evaporate while the account still looked anonymized.

That choice is right for the files' CONTENT and wrong for their PROVENANCE on a declarative host. A host that declares its accounts in its configuration (the supported path on NixOS, ADR-0010 and `docs/nixos.md`) ends up depending, at boot, on two unit files that nothing in its configuration knows about: no rebuild reproduces them, no rollback undoes them, and a reinstall of the machine restores the declared accounts and the declared anonctl binary but NOT the units. The accounts come back with nothing installing their forcing at boot. Worse, a host that works around this by declaring the units ITSELF, from text it maintains by hand, takes on a DRIFT hazard that is strictly worse than the state it was fixing: the copy it maintains and the copy anonctl would write are two definitions of one unit, `/etc/systemd/system` outranks `/usr/local/lib/systemd/system`, and systemd resolves the conflict silently in the host's favour while anonctl's copy sits next to it looking authoritative. Measured on systemd 260: two copies of one unit name produce no diagnostic at all, and `FragmentPath` simply reports the higher-ranked one.

## Decision

**The unit TEXT is exportable, single-sourced from the generator `add` installs through.** Two shapes, one source:

- `anonctl units print --kind shim|nftables --setpriv PATH --shim PATH --env-dir DIR --nft PATH --rules-dir DIR` writes the text to stdout. It is a PURE function of its flags: no file is read, no host is probed, nothing is resolved against `$PATH`, no timestamp is embedded. A missing path is a refusal, never a default, because a unit naming a merely plausible path fails 203/EXEC at the next boot rather than at the command that produced it.
- `share/anonctl/units/*.service.in` ship the same text with each host-varying path left as an `@name@` token, for a packager that wants data rather than execution (it also survives cross-compilation, where running the just-built binary does not).

Both call `systemd.Export`, which calls `TemplateUnit`/`LoaderUnit` -- the very functions `Store.InstallCommon` writes through. There is no second copy of the template anywhere in this repository, including in testdata, and three tests hold that: the printed text is byte-identical to what the install path writes to disk; the packaged `.in` files equal the emitter's placeholder output; and substituting every placeholder in an `.in` file reproduces the installed text exactly (which is what proves the placeholders cover every host-varying value).

**A host may declare that it OWNS those two files, via the marker `/etc/anonctl/units.host-owned`.** With the marker present, `add` and `update` write neither unit file, the legacy `/etc/systemd/system` sweep is skipped, and `rm` never deletes them. The bit is a marker FILE rather than a flag or an environment variable because it must hold for every invocation by every caller: a flag on `add` cannot protect `update` (which also rewrites both files), and an environment variable has to be present in an operator's interactive `sudo`, in a reconcile oneshot and in a rescue shell alike, while being invisible to anyone inspecting the box. A marker is declared like everything else the host owns, so it arrives and departs with the configuration that declares the units.

**The binary paths are PARAMETERS, not lookups.** A host that declares a unit points `ExecStart` at a path from the same pin as the binary. That is why `units print` refuses rather than resolving: the same flags must produce the same bytes on the build machine and on the target, or a derivation calling it is not reproducible.

**The per-account enablement symlinks are NOT exportable and never host-declarable.** `multi-user.target.wants/anonctl-shim@<account>.service` is the one artifact whose NAME says which account slot is in use. A host that declared it would publish that fact to its configuration repository and its git history, which defeats the slot-pool discipline `docs/nixos.md` section 4 exists to protect: a pool declared in full from the first commit reveals a slot COUNT, while a per-account `.wants` entry reveals which slots are live, when they became live, and in what order. Those symlinks stay anonctl's in every mode, in a directory that is writable and survives a reboot.

This works because systemd resolves a `.wants` entry by unit NAME, not by its symlink target. Measured on systemd 260: a `.wants` symlink in a LOWER-precedence directory pointing at a file that does not exist still produces a real `Wants=` dependency, and the instance loads its fragment from the higher-precedence directory and starts. So in host-owned mode anonctl's symlinks keep working unchanged, pointing at a path in its own unit dir that now holds no file.

## Consequences

- **A host that says nothing is unaffected.** No marker means the default unit dir, the default install, the legacy sweep and the teardown all behave exactly as before, which is asserted by test rather than assumed.
- **A declaration anonctl cannot vouch for is refused up front.** Before `add` creates or adopts anything, it asserts that both declared units are present in systemd's search path, that they carry no unsubstituted `@name@` token, that the binaries they name exist AND are absolute, and -- the load-bearing part -- that they AGREE WITH ANONCTL ABOUT ITS DIRECTORIES: the loader's glob must be anonctl's rules dir and the shim's `EnvironmentFile` must be anonctl's env dir. The directory agreement is what anonctl pins itself when it owns the units, and handing the files to the host removes that pin; nothing downstream replaces it, because a glob is not a binary and so the binary sweep skips it. A loader pointed one directory sideways loads nothing at boot, which means no standing baseline default-deny, which is fail-OPEN and silent (the live rules are correct, and the loader is enabled-but-not-started, so the mistake is first evaluated at the boot it breaks). The same reasoning forces the absolute-path rule at BOTH ends: `units print` will not emit a relative binary path, because a unit inherits no useful `$PATH` and `--nft nft` is exit 127 at boot. `add` also refuses when the units exist but anonctl's unit dir is not writable, because the per-account symlink is anonctl's in that mode too.
- **`verify` re-checks the same agreement, because a declarative host changes without running anonctl.** The install-time gate cannot see an edit to a module followed by a rebuild, and the drift it would miss is exactly the fail-open one. `unit-binaries-present` therefore runs the whole host-owned preflight in that mode (same assertion name, so the `--json` contract of ADR-0003 is unchanged).
- **`verify`'s `unit-binaries-present` follows the units.** In host-owned mode it reads the files systemd would LOAD rather than anonctl's unit dir, so the assertion keeps checking the binaries that are actually going to be exec'd. A `/nix/store` path stays acceptable, deliberately: a store path reached from a system closure is a GC root (verified: a declared unit is itself a store file whose reference set contains the binaries it names), so it is genuinely durable, and flagging it would condemn the correct configuration in the same way flagging `/run/current-system/sw/bin` would.
- **`update` no longer re-bakes anything in that mode**, because there is nothing anonctl owns to re-bake. The property the re-bake exists to restore (the units name binaries that exist) is asserted and REPORTED instead of repaired, since repairing would mean writing a file anonctl does not own.
- **Shadowing is reported, never resolved by deletion.** When anonctl's own copy is outranked by another, `add`/`update` say so and name both paths. anonctl does not delete the winner: on a declarative host it is very likely the host's own file, and deleting a declaration is the worse error (it is undone only by a rebuild, and until then the next boot has no unit at all). For the same reason the pre-0.4 legacy sweep, which deletes anonctl units from `/etc/systemd/system`, is skipped entirely in host-owned mode: that directory is exactly where a declarative host puts what it declares, and anonctl cannot tell residue from declaration by path.
