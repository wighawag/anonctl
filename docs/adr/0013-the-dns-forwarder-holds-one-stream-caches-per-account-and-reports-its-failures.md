# The DNS forwarder holds ONE stream per account, caches answers per account, and REPORTS its own failures

## Status

Accepted (0.10.0). Amended by ADR-0014 (0.11.0): the DNS port no longer answers other local uids, which shrinks the cache's timing side channel described below to the account and root.

## Context

The shim's DNS forwarder is one half of the leak-proof seam: every name the account resolves is carried over the endpoint as DNS-over-TCP through a SOCKS CONNECT, the host resolver never sees it, and if the endpoint cannot answer, the account gets no resolution rather than one in the clear (ADR-0011, `internal/shim/dnsforwarder.go`). Until this change it opened a FRESH SOCKS stream for every query and closed it again, with a 5-second deadline on the exchange and an UNBOUNDED dial in front of it.

A field report from a live host (telemaque, 0.9.0, two adopted accounts, system tor on `127.0.0.1:9050`, `work/notes/observations/dns-forced-path-answers-is-single-shot-on-a-path-with-tenfold-variance.md`) measured a forced lookup inside the account's session (`getent ahostsv4 example.com` in `anonctl use`) at a ~2.2s median with a 0.26s-to-3.6s spread, against 2 to 18 MILLISECONDS unforced. Per-query stream opens are exactly what RFC 7766 says DNS-over-TCP should not do, and every name paid one, twice for a `getaddrinfo` asking A and AAAA. **How much of the 2.2s they account for is NOT established**: the same deployed shim's own DNS port, queried directly the same day, answered an A+AAAA pair in ~0.34s. The two measurements differ in their point (through NSS and the nft redirect, versus straight at the port), and the gap between them is open (see the observation note and "Live verification" there).

The same investigation produced a second, worse finding, which is what the operator actually hit. A failed resolution was SILENT. When the exchange deadline fired, or the endpoint was simply down, the query was dropped, the client waited out its own timeout with no signal, and the shim logged nothing. Confirmed against the released 0.9.0 binary: through an endpoint that completes the SOCKS handshake and then goes quiet, the client gets nothing for as long as it waits; with the endpoint dead, the client times out and the log is empty. At the probe, that silence is indistinguishable from an answer destroyed on the way back, and on telemaque `dns-forced-path-answers` went red with a message asserting a conntrack un-NAT drop, which sent the operator to `nft` for an event inside anonctl's own forwarder. `verify` gates `use` and `exec`, so the cost was a locked-out operator with a wrong diagnosis in hand.

Two of the changes below alter what the ENDPOINT can observe, which is why they are recorded here rather than only in the code.

## Decision

**ONE persistent, pipelined DNS-over-TCP stream per account, re-dialled on error or idle** (`internal/shim/dnsupstream.go`). Several queries may be outstanding at once; answers are matched to their waiters by a message ID the STREAM assigns, and the client's own ID is restored on the way back out. The rewrite is not tidiness: two clients can legitimately have the same ID in flight at once, and on one shared connection that collision would deliver one client's answer to the other. A stream with nothing in flight is torn down after 30s, and only then: the teardown never takes a stream with a query on it. Each query has its OWN deadline and its own failure. A query whose deadline expires with nothing received since it was written proves the stream has stopped answering, so the stream is abandoned and the other queries on it retry on a fresh one; a query that expires while other answers keep arriving proves only that its answer was slow, and the stream stays. A query whose stream fails for a reason that is not its own deadline (the peer closed it, another query abandoned it, the idle teardown claimed it as the query arrived) is retried ONCE on a fresh stream, within the same deadline, so a retry never extends a client's wait. The dial is now bounded by the exchange deadline; it had no timeout at all.

**It changes no anonymity property, and the reasoning is the point.** The stream is already per-account: every dial and re-dial carries the `<account>@` isolation username (Tor's `IsolateSOCKSAuth`), which pins its circuit class, and the shim process is per-account under its own dedicated uid. Holding that one stream open therefore links nothing that re-opening it repeatedly did not already link. What the endpoint sees change is the SHAPE of the account's DNS traffic: one long-lived stream carrying N queries instead of N short streams carrying one each. Both are inside one isolation class, so neither is correlatable to anything the other is not; the long-lived one discloses less, because a stream open and close per name is itself a per-name event.

**A per-account answer cache, honouring the answer's own TTL, bounded** (`internal/shim/dnscache.go`). It is a field of one Forwarder, in one account's shim process, never written to disk, and gone when that process ends: no shared store and no box-wide cache, by construction, so no slot can learn anything about another from it. Positive answers are held for the smallest TTL in the answer section, capped at an hour; negative answers, including a NOERROR whose answer section is only a CNAME chain to a name with no record of the asked type, only as far as `min(SOA.TTL, SOA.MINIMUM)` and the chain's own TTLs allow (RFC 2308), capped at five minutes, and not at all without an SOA. What is served back carries the REMAINING TTL. The key is the question's name in its canonical WIRE form (lowercased, length-prefixed labels) plus what changes a correct answer (qtype, qclass, CD, EDNS, DO), and a hit is served with the asker's own question copied in. The wire form is load-bearing: a label may legally contain a dot, so a dotted-string key let the one-label `example.com` and the two-label `example.com` share an entry, and any local uid could plant an NXDOMAIN that blocked the account from resolving that name.

**SERVFAIL is never cached, in either direction.** Not an upstream resolver's SERVFAIL (a statement about that moment, which held would turn one bad second into minutes of an account that cannot resolve a name), and not the forwarder's own (made only after an upstream error, and never passed to the cache, which is filled only from answers that came through the endpoint). It is named explicitly ahead of the general rcode rule that also excludes it, because it is the one exclusion whose absence would be a fail-closed bug dressed as a performance one: a cached "could not resolve" outlives the outage that produced it. Both directions are tested.

**The cache's one honest cost is a local timing side channel, stated at the choice site.** Anyone who can send a query to the forwarder's DNS port can time the answer and learn whether the account has recently resolved a name. That port answered ANY local uid (measured, pre-existing, and recorded as its own observation), so on a multi-user host the observer was not only root; ADR-0014 closes the port to every uid but the account's own. `ForwarderConfig.NoCache` exists as the place an operator-facing switch would land.

**A failed resolution is answered, with a CLASSIFIED reason, and never with silence** (`internal/shim/dnsfailure.go`). The client gets SERVFAIL, carrying no records, under its own message ID, on both listeners. The reason is classified because the two common causes call for opposite next moves:

- **endpoint unreachable**: nothing accepted a connection at the SOCKS endpoint. The anonymizer is down ("your Tor is down").
- **deadline expired**: the endpoint accepted the shim and the lookup ran out of time. The circuit was slow ("your circuit was slow").
- **endpoint refused**: the endpoint is up and failed the CONNECT to the resolver (for Tor, a circuit or exit failure).
- **stream broken**: the stream died mid-exchange and a re-dial did not recover the query.

Unreachable is tagged where the endpoint dial happens (the SOCKS client's forward dialer), so it does not rest on error strings. The reason is reported twice: in the shim's log, `dns: <reason>: ... (SERVFAIL, fail-closed)`, in the register the relay already uses for its drops; and as an RFC 8914 Extended DNS Error on the SERVFAIL, but only when the query carried EDNS, since RFC 6891 allows no OPT in reply to a query without one. glibc sends EDNS when resolv.conf says `options edns0`, as the reporting host's does.

**SERVFAIL on a dead endpoint is not a fallback, and fail-closed is unchanged.** SERVFAIL carries no resolution, and nothing caches it as a negative. A resolver that falls through to a second nameserver lands in this same shim, because anonctl redirects the account's DNS whatever destination it names (`lan-exemption-not-a-dns-hole` asserts exactly that). The only route to an answer in the forwarder remains the SOCKS dial, or a cache entry that itself came through one. The test that used to assert silence with the endpoint down now asserts CONTENT: no address, rcode SERVFAIL, for a name the host could answer trivially, so a leak would show up as an address rather than having to be inferred.

**The exchange deadline is 10s and bounds the dial as well.** With the stream held open the connect is not paid per name, so the room is for the one legitimately slow case left, a cold circuit build. The TCP listener's client deadline was split from it; they had been one 5s deadline, and a longer exchange would have had its answer written to an already-expired client connection.

**`dns-forced-path-answers` FAILS on a SERVFAIL, and says why.** Without this, `dns-forced-path-answers` would have started PASSING on a dead endpoint, because any rcode counted as ANSWERED: making the forwarder honest would have made the verdict lie. The probe's polarity (an answer of any rcode proves the PATH works) stays; the verdict reads the rcode and the reason. To receive the reason, the probe now sends a bare EDNS0 OPT (no options), which is what glibc sends on this host and does not make the probe stand out to the resolver it reaches.

**The forced round trip is measured up to twice before a verdict, with a fresh unique name per attempt.** The check gates `use` and `exec`, and it was single-shot on a path with tenfold measured variance. Each attempt is a full re-measurement with its own counters and control window. The second runs ONLY for outcomes a cold circuit or one lost answer can explain: the query reached the shim and got no answer, or the shim answered SERVFAIL for a slow, refused or broken upstream (`forcedRetryWarranted`). An answer from off the forced path, a query that never reached the shim, and an unreachable endpoint are judged on the first attempt, so none of them can be hidden behind a second-attempt pass. A fresh name per attempt is now doubly load-bearing: uniqueness is what makes the NSS bypass measurable at all (ADR-0011), and re-asking one name would be answered from the shim's new cache. **A pass that needed the second attempt says so**, with what the first attempt MEASURED (its packet fate, not a guessed cause); a first-attempt pass says nothing about attempts, so the phrase is a signal. The retry may separate a lost answer from a broken path; it may never be the silent reason a path passes.

**The failure texts state what was measured and rank the candidates.** The un-NAT branch fires on a counter proving only that A packet left the shim's DNS port during the window, which glibc's own retries can satisfy (and so can a late reply to the NSS probe that runs immediately before). It used to assert the un-NAT-and-drop mechanism as fact. It now reports the observation, notes that which candidate is likelier depends on the running shim's version (a current shim answers every query within its deadline, so silence then points at the return path; an older one drops unresolvable queries silently), and gives the cheap step that settles it: restart the shim and re-run.

**The forwarder header's premise about TCP is corrected.** It said resolv.conf carries `options use-vc`, a premise inherited from the netcage code this was mirrored from; anonctl writes no such option and the reporting host has none, its glibc queries over UDP. TCP remains mandatory for the reasons that do hold everywhere: truncation retries (RFC 7766) and hosts that do set `use-vc`.

## Consequences

- **An operator can SEE a failure now, and tell down from slow.** Measured on telemaque against the released binary, querying each shim's port directly: with the endpoint dead, 0.9.0 gives the client nothing (it timed out at 8s) and logs nothing; this change answers SERVFAIL in about a millisecond and logs `endpoint unreachable`. With an endpoint that accepts and goes quiet, it answers SERVFAIL at the 10s deadline and logs `deadline expired`. `verify` names the same two reasons.
- **Latency, measured at the forwarder's own port, not through the account's path.** On telemaque, 2026-09-25, from an unprivileged uid, each commit's binary against `anon-01`'s deployed 0.9.0 shim in the same circuit class, interleaved with the leg order alternating, ten samples, medians: one lookup (A+AAAA, a fresh name) 0.361s to 0.153s with reuse alone; five lookups of one name, the shape a page load has, 1.722s to 0.214s with the cache. On a SOCKS endpoint adding 250ms one-way: one lookup 1.036s to 0.529s, a five-name burst 5.157s to 2.723s.
- **Reuse alone buys little on a fast warm circuit, and the cache does the heavy lifting on real workloads.** Reuse halves the circuit traversals per lookup, so its value scales with what the circuit costs; on a warm circuit that is tens to low hundreds of milliseconds. The order-of-magnitude change on repeat lookups is the cache.
- **The account's real path is unverified by the change's author**, who had no root. Whether the ~2.2s the operator measured through `getaddrinfo` inside `use` falls with this change, and by how much, is the first live-verification step in the observation note, along with a healthy `verify` and a deliberate dead-endpoint run. If the real path is still ~2s while the port answers in ~0.3s, the cost lies between `getaddrinfo` and the forwarder, which would be its own finding.
- **A client may give up before the shim does.** glibc's own per-query timeout is 5s, so on a slow circuit a client can retry before the 10s deadline fires; the retry rides the same stream rather than opening another.
- **The shim holds one more file descriptor per account while DNS is in use**, and one Tor stream stays open for up to 30 idle seconds.
- **A stale answer is possible where none was before**, bounded by the TTLs above. The cache does not survive a shim restart, so `systemctl restart anonctl-shim@<account>` is the escape hatch.
- **A running shim keeps its old binary until restarted.** After an upgrade, a shim that was not restarted still drops failures silently, and verify's texts name that possibility and the restart that rules it out.
- **The cache's side channel is not mitigated here.** Closing it means a uid or peer-credential filter on the shim's DNS port, which would also close the pre-existing ability of any local uid to use the account's circuit for lookups. That is a separate change with its own measurement to do.
- **Not built here: a per-account SOCKS front door so the exit resolves names.** Proposed from the fleet side; these measurements make it worth less than assumed (the cache, not removing a round trip, is what moves real workloads), and it adds a listening surface with a security precondition this work exposed. Recorded as an idea with its two conditions (`work/notes/ideas/per-account-socks-front-door-for-exit-side-resolution.md`).
- **The forwarder's TCP listener still answers the queries on one client connection one at a time**, so a `use-vc` client's A and AAAA are serialised there (RFC 7766 says SHOULD process concurrently). It does not affect hosts whose glibc queries over UDP, and it was left out of this change.

## Amendment: what an adversarial review of the first implementation found

A review of the six commits that introduced this (before release) found no blocker and all four must-not-regress properties holding (fail-closed, both listeners alike, the isolation username on every dial, the probe staying a measurement), with one qualification on the last. It also found real defects, fixed in follow-up commits rather than folded back, so a bisect landing on one of them is informative:

- **The retry could hide a structural failure** (the qualification). It retried on anything but a non-SERVFAIL answer, so an answer from off the forced path followed by a good second attempt passed, described as a cold circuit. The policy above replaces it.
- **One query's deadline failed every query on the stream**, reported as "deadline expired" for deadlines that had not expired, and not retried. Each query now has its own failure.
- **The idle teardown could take a stream with a query on it**, and a query racing it got an unclassified SERVFAIL. The teardown now takes only an empty stream, in one step, and the race is retryable.
- **An answer could be discarded** when it arrived in the same instant its stream died (Go picks between ready select cases at random).
- **The dotted-string cache key** described above, and a CNAME chain to nothing held for up to an hour.
- **Tests that could not fail**: the re-dial test (the retry path was never reached, so it passed with the retry deleted), the cache-miss test (it never took the endpoint down), the dead-endpoint test (it passed on silence), and the TTL countdown test (it passed on a replayed TTL). Each now fails when the property it names is broken, checked by deliberately breaking it.
- The original rationale for the re-dial ("the close often shows only on write") was wrong for this design, as the review showed: a dedicated reader sees a peer close at once. The retry exists for failures that land on a query in flight, as stated above.

One more defect was found by the new tests rather than the review: after one slow query timed out, the forwarder retired a healthy stream, so the next query dialled a second one while the first lingered. Only a dead stream is retired now.
