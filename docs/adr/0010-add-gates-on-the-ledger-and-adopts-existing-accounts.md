# `add` gates on anonctl's ledger, not on the passwd table, and adopts an existing PAIR

Status: accepted

## Context

`add` refused an account whose passwd entry already existed, up front, before any mutation. The stated intent of that guard was "a second `add` never silently re-applies a (possibly different) endpoint/config", and `getent passwd <account>` was taken as a sufficient proxy for "anonctl already set this account up".

It is not a proxy for that, and on one class of host the difference makes anonctl unusable. NixOS with `users.mutableUsers = false` treats its configuration as the authoritative user database and deletes every undeclared account at each activation, which means at every `nixos-rebuild switch` and every boot. anonctl creates its accounts out of band, so they are undeclared by construction and are deleted, leaving loaded nft tables governing freed uids while `/etc/anonctl` still records the account as jailed (measured, with the boot journal, in `work/notes/findings/nixos-account-conventions-break-anonctl-provisioning.md`). The fix on the host side is to DECLARE both accounts with pinned uids, which also closes the UID-reuse hazard, since a pinned uid cannot drift or be handed to a stranger.

That fix and the guard were mutually exclusive. The moment the accounts are declared they exist, so `add` refused, and no forcing was ever installed. The resulting state was the worst available: both accounts present, nothing jailing them, and no verb that would fix it (`update` reads the persisted config, so it targets an account anonctl already manages). `docs/nixos.md` and the README already documented adoption as the supported path; the code refused it.

## Decisions

- **The gate reads anonctl's LEDGER (`/etc/anonctl/accounts/<account>.json`), not the passwd table.** A record means anonctl manages the account and `add` refuses, pointing at `update` (change it) or `rm` + `add` (re-install its forcing). No record means `add` proceeds. This is what the guard was always about: the thing that must not be silently re-applied is anonctl's own endpoint/exemption record, and a passwd entry says nothing about whether such a record exists. A record that exists but cannot be READ (corrupt, unreadable) is a loud failure, never treated as absent.

- **Accounts that exist without a record are ADOPTED, not refused.** `add` creates nothing (`provision.Add` is already a per-account no-op), does not seed the home and does not write the login env (both stay scoped to `res.Created`: an adopted account's home belongs to whoever declared it), discovers both uids from the box and installs the forcing against those. The uids are always read, never assumed, because the whole point of the declarative host is that it chose them.

- **Adoption is strictly a PAIR: half is REFUSED, naming both accounts, and never completed.** A login account without its shim (or the mirror) is the half-provisioned state `provision.go:145` describes. Adopting it would install forcing whose endpoint-reachability exemption names a shim uid that does not exist, leaving an account that is fail-closed but permanently unusable while anonctl reports it as set up. Creating the missing half is worse on the host that needs adoption: an account anonctl creates there is undeclared, so the next activation deletes it and the half-state returns at every boot. A missing half on such a host means the operator's configuration is wrong, and that is where it has to be fixed.

- **An adopted uid must be owned by that account ALONE.** `useradd` refuses a duplicate uid unless explicitly told otherwise, so an account anonctl created is unique by construction; an adopted one is only as unique as whoever made it (`useradd -o -u`, or a host that does not enforce uniqueness). The rules match `meta skuid`, which names a uid and not an account, so forcing a shared uid would silently redirect and default-deny an unrelated account's egress. `add` asks two questions, because neither covers every host: a REVERSE lookup (`getent passwd <uid>`), which resolves through NSS and so is answered even by a directory backend that refuses enumeration but sees only the first match, and an ENUMERATION, which sees local duplicates that sort after the anon account. Either one naming a different account is a refusal, naming it. Neither can prove a negative on a non-enumerable backend, so that limit is stated in a note rather than turned into a refusal that would make anonctl unusable on every directory-joined host.

- **The create-vs-adopt decision is taken from the read at MUTATION time, not the one before the prompt.** Both reads run the pair rule, but only the second one decides, because a pair that appeared while the operator was choosing an endpoint turns a creation into an adoption, and deciding from the stale read would install forcing on accounts that never passed the shared-uid check and were never disclosed. Both paths into "this is an adoption" go through one function, so the second cannot silently skip what the first enforces.

- **An UNREADABLE record is never treated as an absent one, on any surface.** The gate fails loud rather than re-adding over a config it could not read, and the identity check classifies it as its own failing state (`record-unreadable`) rather than "nothing to compare". The commonest cause is an unprivileged `status` against a root-only record, and the collapse would have printed a passing identity line for an account whose uid may have drifted, i.e. a green for the exact condition the check exists to surface.

- **The identity comparison is one decision (`verify.AccountIdentity.State()`) rendered by two surfaces.** `verify` keeps it as its short-circuiting precondition; `status` now renders it as an `identity:` line and as `identity.state` under `--json`, with distinct results for "the passwd entry is gone while anonctl records the account as forced" (`account-missing`), "it exists under a uid the rules do not govern" (`uid-mismatch` / `shim-uid-mismatch`), "it exists but anonctl has no record yet" (`unrecorded`) and `ok`. `status` stays exit-code neutral: it reports, `verify` adjudicates.

## Consequences

- An account that exists and is unmanaged is now MUTATED by `add` (forcing installed against it) where it was previously refused. That is the intended new capability, and it is announced before anything happens (`adopting: ...`, printed before the endpoint prompt) so an operator who typed the wrong name can abort. Everything `add` does to an adopted account is anonctl's own state; the account itself is untouched.
- The recovery for a drifted uid is `anonctl rm <account>` (a bare `rm` tears the stale forcing, ledger record and marker down while leaving the accounts and homes intact) then `anonctl add <account>`, which re-adopts and re-installs against the current uids. The previous advice, a bare re-`add`, dead-ended on the old gate and dead-ends on the new one; the assertion details now name the sequence that works. `update` is deliberately NOT that path: it re-applies the RECORDED uids, which are exactly what is stale.
- The pair rule makes one previously-working shape an error: an interrupted `add` that left a login account with no shim is now refused instead of completed. `anonctl rm --purge-account <account>` clears it, and the refusal says so.
- The pair rule is enforced against a READ, which cannot be atomic with the provisioning that follows it. It is re-asserted immediately before `provision.Add` (so the window is not the length of the interactive endpoint prompt), and the residual race is REPORTED rather than assumed away: if the accounts were there at the check and one was created at provisioning, `add` says loudly that it created what it meant to adopt, and on a host that deletes undeclared accounts, names the consequence. It still installs the forcing, because the uids are read after that point and refusing would leave those accounts with none.
- Because the record is now the gate, a `rm` that fails BEFORE it reaches `ConfigStore.Remove` (for example a `systemctl` failure during teardown) leaves the record in place, and `add` keeps refusing. That ordering is pre-existing (teardown is proceed-and-report, but `forcing.Remove` returns on its first error), and it is why the refusal names the record's path: deleting that file is a documented way out. Making `forcing.Remove` proceed-and-report internally would close it and is left as separate work.
