# CONTEXT: anonctl domain language

The domain glossary for `anonctl`. Agents and skills use THIS vocabulary when naming modules, tests, and discussing the system. Architectural rationale lives in `docs/adr/` (decisions); product framing lives in `work/specs/`.

## What anonctl is

anonctl is a Linux-only setup-and-verify manager that provisions a dedicated Unix user and forces all of that user's egress through an anonymizer (Tor or any socks5h endpoint) at the kernel level, fail-closed and default-DROP, then verifies it is leak-free. It applies the rules itself as root (like ufw/firewalld), and exposes a marker (`/etc/anonctl/<account>.json`) that sibling tools read to avoid double-anonymization.

anonctl is a SETUP + VERIFY MANAGER, not a runtime wrapper: it is NOT in the data path. The kernel nftables rules plus the Tor/redsocks config ARE the data path; anonctl installs, verifies, and manages them. Day-to-day the user logs into the account natively (`sudo -iu <account>` / `su - <account>`) and the kernel does the anonymizing; anonctl is out of the loop at runtime.

## Core domain terms

- **anon account / `anon-<name>`**: the dedicated Unix user whose egress anonctl forces. `anon` is the default account; `anon-<name>` are named ones. anonctl OWNS this generic "anonymized account" naming (distinct from anon-pi's `anon-pi` / `anon-pi-<name>` hardened accounts).
- **per-UID kernel forcing**: the mechanism: nftables `meta skuid` rules keyed on the account's UID that transparently redirect the UID's TCP into a per-account shim (or drop it), so anything the user runs is anonymized with no per-app proxy config. UNIFORM: there is one forcing mechanism, not a per-backend split.
- **shim**: anonctl's own static Go binary, one instance per account, on a per-account loopback port: a transparent TCP-to-SOCKS relay (reads the original destination via `SO_ORIGINAL_DST`) plus a DNS-over-SOCKS-TCP forwarder (reused from netcage's `netcage-dns`). It relays the forced traffic to the account's socks5h endpoint. Not a distro `redsocks` dependency (leak-proof invariant stays in our code). Runs under a distinct dedicated shim UID so only it (never the anon UID) can reach the upstream endpoint.
- **endpoint**: the socks5h proxy an account is forced through. anonctl does NOT manage its lifecycle (it can scan for and suggest one, netcage-style). Tor's SOCKS port is the default endpoint; a plain socks endpoint (Mullvad local SOCKS, wireproxy, `ssh -D`, wireproxy-chained-with-gost) is another.
- **scan-and-offer**: `add`'s no-`--endpoint` resolution. It runs `endpoint.Scan` (probe 9050/9150/1080, CONFIRM SOCKS5 via a real RFC1928 handshake, mirror netcage `detect-proxy`), then `endpoint.BuildOffers`/`Choose*` decide the outcome: DEFAULT to a confirmed Tor (tor-shared) endpoint, PROMPT interactively (evidence-only, never label the provider; a peruser endpoint already owned by another account is shown IN USE and is not selectable, reusing the task-1 claim set), and fall back FAIL-CLOSED non-interactively (Tor-if-confirmed, else refuse, never configure a dead default). The choice layer is PURE (offers + a `takenBy` predicate + interactive bool); the DialProber scan, the TTY check, and the prompt read are impure seams. The chosen endpoint still passes `claimEndpoint` (the enforcement; the annotation is advisory).
- **endpoint share-class**: the axis that matters: `tor-shared` (per-username SOCKS-auth isolation available) vs `socks-peruser` (single identity). A `tor-shared` endpoint is safe across many accounts because anonctl dials it with a per-account `<account>@` SOCKS username (Tor `IsolateSOCKSAuth` gives a distinct circuit/exit per account). A `socks-peruser` endpoint is one identity and may be used by AT MOST ONE account (else the accounts are cross-identifiable); anonctl refuses/flags sharing it. The refusal is ENFORCED at `add`/`update`: anonctl builds the endpoint Registry from the on-disk account configs (`accountconfig.List` -> `BuildRegistryExcluding` -> `Registry.Claim`, the target account excluded so its own re-add is idempotent) and REFUSES pointing a second account at an already-claimed `socks-peruser` endpoint BEFORE any nft/systemd mutation. A `tor-shared` endpoint is never refused (the Registry tracks only peruser owners, since tor is share-safe). A corrupt sibling config fails the guard LOUD, never a silent pass.
- **fail-closed / default-DROP**: if the endpoint is unreachable, the UID's traffic is dropped, never sent in the clear. The default policy for the UID is DROP; the anon UID may reach ONLY its own shim's loopback port, nothing else.
- **leak-free**: DNS goes via the anonymizer (never plaintext); IPv4 AND IPv6 are both handled (no v6 bypass).
- **NSS bypass**: the class of host where the account's NAME RESOLUTION happens in ANOTHER PROCESS under ANOTHER UID, so `meta skuid` cannot govern it: an nscd-protocol daemon (nscd/**nsncd**, which glibc consults for `hosts` BEFORE `nsswitch.conf` is read at all, so it is invisible in that file), or a delegating NSS module (`resolve`/systemd-resolved, `mdns`/avahi, `mymachines`/machined, `sss`, `winbind`). It is the NSS instance of the v0.4.0 chain-bug principle: A RULE KEYED ON SOCKET OWNERSHIP CANNOT SEE WORK DONE IN ANOTHER PROCESS. anonctl neither fixes it (the daemon serves every uid on the box; forcing its egress is out of scope) nor tolerates it silently: `add` REFUSES a host with a BROAD provider (one that answers arbitrary names) unless `--allow-nss-bypass`, a NARROW provider (a bounded name class like `.local`) is disclosed and allowed, and `verify` MEASURES it on every run regardless of the flag. Detected by `internal/nssbypass`, decided by ADR-0011.
- **measured DNS confinement**: the rule that the DNS assertions observe rather than infer. `dns-remote` (the account's own lookup was carried into the shim), `dns-nss-not-bypassed` (a lookup put a query on the account's OWN sockets at all) and `dns-forced-path-answers` (a query through the redirect actually COMES BACK) all rest on a unique, ABSOLUTE, bare-random `.invalid` probe name nothing can have cached and that carries no product string, pid or timestamp (it is seen by the endpoint's upstream resolver; the trailing dot stops glibc appending the host's own `search` domain to it), looked up AS the anon UID, watched by nft counters planted at output priority -300 (pre-nat: did the account emit a query) and 50 (post-nat: did it reach the shim). The uniqueness is load-bearing: a cacheable name can complete with NO query on any socket, so it cannot distinguish "another process resolved it" from "it was already known". The DETECTOR IS NEVER THE AUTHORITY: a detected provider with a clean measurement PASSES, and an unknown daemon fails just the same. This REPLACED an inferred check that returned `hostSaw=false` hardcoded and therefore reported clean on a host where the account's DNS was both leaking and completely broken.
- **account-identity**: verify's PRECONDITION assertion, checked before any probe: the login account and its shim still EXIST and still OWN the uids anonctl recorded in the account config (the uids the loaded tables and the shim unit actually govern). It SHORT-CIRCUITS the run when it fails, because every other probe keys on `meta skuid <uid>` and dials AS that uid, so a deleted or recreated-under-a-new-uid account yields probes that run perfectly well while answering a question about somebody else's uid. The operator would read a scatter of leak assertions and never the one true finding. This is the NixOS `users.mutableUsers = false` case (activation deletes every undeclared account at each boot); see `docs/nixos.md`. The DECISION is `verify.AccountIdentity.State()`, one of `ok` / `unrecorded` / `account-missing` / `shim-missing` / `uid-mismatch` / `shim-uid-mismatch` / `record-unreadable` (that last one is load-bearing: a record that could not be READ is NEVER collapsed into "no record", because the ledger is root-only and the collapse would print a passing identity line for a possibly-drifted account); `verify` renders it as the precondition assertion and `status` renders it as its identity line (plus `identity.state` in `--json`), so the two surfaces can never disagree about it. It is also what makes an ADOPTED account safe to live with: it is the thing that catches a uid drifting out from under the forcing.
- **adoption**: `add`'s path for accounts that ALREADY EXIST in the passwd table but that anonctl has no LEDGER record of. It creates nothing (`provision.Add` is a per-account no-op), seeds no home and writes no login env (both are scoped to `res.Created`, and an adopted account's home belongs to whoever declared it), discovers the uids from the box (never assumes them: the declaring system chose them) and installs the forcing against those. It is what lets anonctl run at all on a host that declares its users, where creating accounts out of band is not an option. Adoption is strictly a PAIR: the login account and its `-shim` must both exist, or neither. It also refuses a uid SHARED with another passwd entry: `useradd` guarantees uniqueness for accounts anonctl created, an adopted uid has no such guarantee, and `meta skuid` names a uid rather than an account, so forcing a shared uid would silently jail the other account too. Half a pair is REFUSED naming both accounts, never completed, because forcing installed over a shim account that does not exist names a uid nothing runs as, and because a half anonctl created on a declarative host is deleted again at the next activation.
- **ledger**: `/etc/anonctl/accounts/<account>.json`, anonctl's own record of the accounts it MANAGES (uids, endpoint, exemptions, shim ports). It is the gate `add` reads: an account WITH a record is refused (a second `add` must never silently re-apply a different endpoint/config, which was always the guard's real subject), an account WITHOUT one is created or adopted. Deliberately NOT the passwd table: passwd existence says nothing about whether anonctl configured anything, and gating on it refused exactly the declarative hosts that need adoption. The same file set is the endpoint claim set (cross-identification guard) and the shim-port reservation ledger.
- **verify**: the trust anchor and the signature ONGOING verb (run after setup, after reboot, after a Tor/kernel/nftables change). It asserts the account is anonymized (for a Tor endpoint: the exit is a confirmed Tor exit via check.torproject.org / onionoo, fetched over Tor FIRST, since it reports the exit IP too and a generic IP-echo is only a FALLBACK: one blocked echo must never fail this assertion on a correctly jailed account; otherwise, or under `--skip-tor-exit-check`: the exit differs from the host), DNS is resolved remotely via the endpoint AND on the account's own sockets AND actually answers (see measured DNS confinement), a direct connection from the UID is actually DROPPED (the leak test), the split-tunnel stays tight with a LAN exemption active, and the boot invariant holds. The DIRECT host-IP baseline (which reveals the real IP) is fetched ONLY when the exit-differs diff is the proof (non-Tor, or `--skip-tor-exit-check`), NOT on the Tor-default path where the Tor-exit confirmation is the proof, so `verify` does not gratuitously reveal the real IP. `add` runs this same gate INLINE at the end of provisioning (warn-and-continue: forcing is fail-closed regardless, so add still succeeds when the endpoint is not yet up). Named assertions, non-zero exit on failure, `--json` for machines. Mirrors netcage's `verify`.
- **marker**: `/etc/anonctl/<account>.json`, versioned JSON (`schemaVersion`, `account`, `uid`, `endpointClass`, `createdAt`, `anonctlVersion`, and the optional `bootId`; deliberately NO endpoint URL/creds since it is world-readable). The dependency-free contract anon-pi / netcage read to detect "this account is already kernel-anonymized" and skip re-forcing (the double-anonymization guard). Written only after `verify` passes; a coordination claim, not a live security proof. The name prefix is a hint only; `anonctl status --json` reads the same truth. `bootId` is the kernel boot the proof was made in, because the marker OUTLIVES the proof: after a reboot the rules are re-loaded and nothing re-verifies, so a marker written in an earlier boot reads exactly as green as one written a second ago. Absent `bootId` means UNKNOWN boot (an older marker, or a host with no `/proc/sys/kernel/random/boot_id`), never a mismatch.
- **config root**: `/etc/anonctl` itself, and the fact that ONE place (`anoncore/configroot`) owns it and its mode, rather than each store creating it as a side effect of `MkdirAll` on its own subdirectory. `MkdirAll` creates missing PARENTS at the leaf's mode and does nothing at all to an existing directory, so with three writers under one root (`marker` 0755, `accountconfig` 0700, anonctl's `systemd` env/rules 0700) whichever wrote first silently decided the shared parent's mode. It was always the ledger, because `add` writes the ledger before its inline verify writes the marker, so `/etc/anonctl` was 0700 on every real box and the credential-free marker could not be read by the unprivileged consumers it exists for. The root is 0755 and is CHMOD'ed explicitly at write time (which also repairs a box provisioned by an older build); every child asserts its OWN mode in the same call, so a traversable root widens nothing inside it. A 0755 root does expose the NAMES of accounts that have markers, which is intended: the marker is credential-free and a local account name is already visible in `/etc/passwd`. It ALSO removes the incidental protection that the 0700 root was giving the two OPERATOR-placed paths anonctl does not create, `default-home/` (dotfiles, tool configs, populated with a plain `sudo cp` that leaves 0755/0644) and `defaults.json`; anonctl therefore asserts 0700/0600 on them itself (`defaults.Store.Tighten`, called once at the root dispatch chokepoint, warning rather than failing). Widening the parent must widen NOTHING inside it, and that rule covers the paths anonctl merely reads, not only the ones it writes.
- **probe**: the cheap live "is this account jailed RIGHT NOW" verb, the middle ground between the marker (a durable CLAIM, free to read, survives reboots the rules may not) and `verify` (a live, network-touching, tens-of-seconds PROOF). Three checks, no network: the marker is present, its recorded uid IS the account's live uid, and the account's nft table is actually loaded AND funnels that uid into the fail-closed chain. Named reason per failure (`no-marker`, `marker-unreadable`, `account-missing`, `uid-drift`, `rules-unreadable`, `table-missing`, `uid-not-governed`), NON-ZERO EXIT when not jailed, and an undetermined check is never a pass. It lives in anonctl because the per-account table naming (`anonctl_<account>`) is anonctl's PRIVATE convention: a consumer grepping the ruleset for it is a coupling anonctl did not choose and could not refactor away. It does NOT replace `verify`: it proves the rules are loaded and attributed, not that the forced path is leak-free.
- **trigger surface**: `/etc/anonctl` and `/etc/anonctl/accounts` are a PROMISED, STABLE surface for downstream automation to watch (inotify) and reconcile on. A ledger record `<account>.json` appears under `accounts/` on `add`; a marker `<account>.json` appears in the root on a green `verify`; BOTH vanish on `rm`. That is the whole contract, and it is deliberately not a hook mechanism: a watch is cheaper than any callback system anonctl could ship, needs no registration, survives anonctl not running, and cannot leave a half-run hook behind. Downstream watchers depend on this, so it is a promise now rather than an accident of implementation: the two directory paths and those three transitions do not change without a version bump and a note in the release. (What a watcher may key on: the FILENAMES. Contents are a separate contract - the marker's JSON is versioned by `schemaVersion`, the ledger is anonctl-private and root-only.)
- **LAN exemption**: a narrow, guardrailed hole (anonctl's `--allow`, mirroring netcage's `--allow`) exempting a configured RFC1918 `host:port` (e.g. a local LLM at `192.168.x.x`) from forcing, scoped to the exact host and port, not a broad allow. A **port is MANDATORY** (an all-ports / bare-IP form is rejected loudly): an all-ports hole to a host running a forwarding proxy would be a deanonymization vector, so an exemption always names exactly one service (ADR-0007).
- **Tor-over-Tor / double-anonymization**: running an already-anonymized account through a second anonymizer. anonctl makes this DETECTABLE (via the marker/verify) and documents the caveat so it is avoided.
- **unit dir**: anonctl installs its units into `/usr/local/lib/systemd/system` (systemd's documented home for "system units installed by the administrator"), NOT `/etc/systemd/system` (a read-only Nix store symlink on NixOS) and NOT `/run/systemd/system` (writable there, but CLEARED AT BOOT, which would make the forcing evaporate on reboot). One default serves both Debian and NixOS, so nothing does a distro check. Because `/etc/systemd/system` OUTRANKS it in the load path, an upgrade SWEEPS any pre-0.4 units out of there (`Store.MigrateLegacyUnits`): a leftover copy would shadow the new one and silently keep serving the old definition. Override with `ANONCTL_UNIT_DIR` (absolute paths only) if a host truly needs it.
- **self-managed enablement**: anonctl writes its OWN `.wants/` symlinks (`<unitdir>/multi-user.target.wants/anonctl-shim@<account>.service`, `<unitdir>/sysinit.target.wants/anonctl-nftables.service`) instead of shelling out to `systemctl enable`. `systemctl enable` always writes into the scope's CONFIG dir (`/etc/systemd/system`) regardless of where the unit file lives, so it cannot work on a host where that dir is read-only; systemd, by contrast, honours `.wants/` in EVERY unit load-path dir. Consequence worth knowing: `systemctl is-enabled` reports `disabled` for these units even though they are genuinely wired to boot, because it inspects only the config dir. The truthful checks are `Store.IsUnitEnabled` or `systemctl show <target> --property=Wants`.
- **resolved unit binaries**: the absolute paths the generated units run (`anonctl-shim`, `setpriv`, `nft`) are RESOLVED at install time and baked in, never assumed from FHS convention: `/usr/bin/setpriv` and `/usr/sbin/nft` do not exist on NixOS. (`/bin/sh` in the loader is the one literal left; it exists on both targets and resolving it would be circular.) `add` REFUSES to force an account when one cannot be resolved, because a unit naming a missing binary fails only at the next boot, and for the nftables loader that failure is fail-OPEN (no baseline default-deny, so the anon UID egresses freely with the host's real IP). The refusal happens BEFORE `provision.Add` creates the account (`systemd.PreflightUnitBinaries`): refusing late would leave an account that EXISTS with no unit installed, which is the fail-open case itself. `verify`'s anon-UID probe uses the same resolution, so the trust anchor is not pinned to `/usr/local/bin`. **The resolved path is baked VERBATIM and the symlink is never resolved:** on NixOS `/run/current-system/sw/bin/nft` is stable across rebuilds while the `/nix/store/<hash>-.../bin/nft` that `EvalSymlinks`/`realpath` returns is garbage-collected on the next update, which would leave `ExecStart` pointing at a missing file (`203/EXEC`), the loader dead and the account unjailed weeks later. `exec.LookPath` returns the `$PATH` entry verbatim and `filepath.Abs` preserves it; `os.Executable` does NOT (it resolves), so the shim's sibling rule passes through `Resolver.preferStableAlias`.
- **enable-then-migrate**: `add` enables the units before sweeping the legacy dir, and the sweep ADOPTS each enablement (re-creating it in the new unit dir) rather than just deleting it. Both rules exist for interrupted/multi-account cases: a delete-only sweep silently de-enables every account that is not the one being added, and migrating first can leave the loader enabled nowhere. Failures here are invisible until a reboot, which is why they are ordered rather than trusted.
- **reboot persistence**: the forcing survives a reboot via anonctl-owned, anonctl-applied artifacts (the ufw stance): the per-account shim as a systemd `@`-template unit (`anonctl-shim@<account>.service`, one instance per account under its dedicated shim UID; `add` enables it via anonctl's own symlink and `start`s it, `rm` `stop`s it and removes the symlink), and the ruleset loaded at boot by anonctl's OWN early loader unit (`anonctl-nftables.service`, `WantedBy=sysinit.target`, `DefaultDependencies=no`, `Before=network-pre.target`) which `nft -f`s anonctl's per-account rule files (the standing baseline default-deny + the forcing tables) INDEPENDENT of the host's `nftables.service` (which Debian ships disabled). This REPLACED the earlier `nftables.service` drop-in, which rode on a host-owned unit anonctl never enabled and so leaked the real IP after a reboot. anonctl does NOT own the endpoint's boot lifecycle (enable your endpoint, e.g. `tor.service`, yourself).
- **baseline default-deny**: the anon UID's standing RESTING STATE: a tiny, standalone per-account `inet` table (`anonctl_baseline_<account>`), SEPARATE from the forcing table, that DROPs the anon UID's real (non-loopback) egress and RETURNs loopback. Applied at `add`-time BEFORE forcing and persisted as its own always-loaded artifact. It is the mechanism behind the inverted boot invariant: forcing (the nat redirect) rewrites the anon UID's dst to a loopback shim port before any filter chain, so the baseline never drops FORCED traffic, but with forcing absent the baseline is all there is and the anon UID is DROPPED.
- **boot invariant**: the load-bearing property "at no point during boot does the anon UID have direct egress". It holds by INVERSION: the anon UID's resting state is the baseline default-deny (DROP), and forcing only ever OPENS the shim path, so "the anon UID has no anonctl forcing loaded" means DROPPED, not free. The worst case is dropped-until-shim-and-endpoint-are-up, never leaking, AND forcing-absent is dropped-not-free. Asserted by `verify` and by a reboot-equivalent early-boot integration test; the definitive proof is a real-host reboot (plus a flush-the-forcing-table-still-dropped check).
- **account config**: anonctl's OWN per-account at-rest operational record (`/etc/anonctl/accounts/<account>.json`, root-only 0600) holding the endpoint + share-class, the shim loopback ports, and the UIDs. It is the source of truth the boot re-apply and `update`/`reconfigure` read. DISTINCT from the world-readable, credential-free marker: the config is anonctl-private and may carry the endpoint address the marker must never hold.
- **home template / seed-home**: a template DIRECTORY whose contents `seed-home` copies into an anon account's home, so anonctl can populate a fresh account with operator-chosen files (dotfiles, a tool config) instead of the near-empty skel home. GENERIC: it copies arbitrary files and knows nothing about pi or a model provider. Two load-bearing rules: a per-file COLLISION is an error unless `--force` (a seed never silently clobbers), and setuid/setgid bits are STRIPPED on copy (a template must never introduce a setuid binary, the uid-transition escape). `--force` lives ONLY on `seed-home`; `add` never overwrites and seeds only on FRESH creation (never on an adopted account, whose home is not anonctl's to populate).
- **add-time defaults**: anonctl's BOX-WIDE defaults under `/etc/anonctl/`, the values `add` falls back to when the operator names no flag, so a bare `anonctl add <name>` lands a ready-to-use account. Two of them, sourced differently: the **default home** is a directory-EXISTS convention (`/etc/anonctl/default-home/` present = seed a fresh account from it; there is NO config key, populate it with `sudo cp`), and the **default LAN exemptions** live in `/etc/anonctl/defaults.json` (`{"allow":[...]}`, root-owned). A CLI flag OVERRIDES a default; a default exemption is re-validated through the SAME `lanexempt` guardrail as the flag (a port is mandatory too), so it is never a quieter path to a leak. See ADR-0006 and ADR-0007.
- **update / reconfigure**: the verb that changes an account's endpoint (`--endpoint`) and re-applies the rules FAIL-CLOSED, re-applying the nft rules (an atomic table replace: the default-DROP is never absent) BEFORE restarting the shim, so there is never a window of un-anonymized egress during a reconfigure.
- **promptGuidance**: the per-repo NUDGE namespace in `dorfl.json` whose members (currently just `testFirst`) strengthen the wording in the worker's in-band prompt. NOT a gate: the `verify` step is still the only acceptance bar. Omitted means off; absence is the default.
- **work/ contract**: the on-disk system this repo uses, defined by the reference docs in **`work/protocol/`** (copied here by `setup`): `WORK-CONTRACT.md` (the contract), `CLAIM-PROTOCOL.md`, `REVIEW-PROTOCOL.md`, `task-template.md`, `spec-template.md`, `ADR-FORMAT.md`. Three REGIME umbrellas (`notes/` capture buckets, `tasks/` the build board, `specs/` the spec lifecycle) plus top-level `questions/` and `protocol/`. One markdown file per item, status = the folder it lives in (never a field). Capture buckets: `notes/ideas/` (proposed), `notes/observations/` (spotted, unverified, append-only), `notes/findings/` (verified external/domain ground truth, each with a `source:`). ADRs (`docs/adr/`, format in `work/protocol/ADR-FORMAT.md`) record what WE decided and why.

## Sibling tools (context, not dependencies)

- **netcage** (Go): a Linux network-jail that runs a container in a netns and forces ALL its egress through a configurable socks5h proxy (fail-closed, per-CONTAINER). anonctl reuses netcage's findings/idioms where they transfer (fail-closed language, `verify` assertions, the narrow LAN hole).
- **anon-pi** (TypeScript/npm): launches the pi coding agent inside a netcage jail; its hardened mode provisions a dedicated `anon-pi` Unix account. anonctl is a DIFFERENT model: per-UID kernel forcing for a whole account, not a per-container jail. netcage/anon-pi compatibility inside an anonctl account is a LATER concern, out of scope for v1.
